# MCHOSE K99 V2 HID 协议（互操作说明）

本文记录 Linux 客户端实现的 K99 V2 **2.4G 接收器**与 **USB 有线**协议。内容来自对公开 HUB 网页客户端的静态分析，并用真机只读/幂等写回验证。它不是官方文档，也不包含官方代码或资源。

## 1. 设备识别

2.4G 接收器在 Linux 中枚举为：

- USB VID/PID：`05ac:024f`（伪装成 Apple Aluminium Keyboard）
- HID 产品字符串：`Compx 2.4G Wireless Receiver`
- 两个 HID 接口：
  - 接口 0：键盘/厂商混合，hidraw 名称相同；
  - 接口 1：鼠标 + 厂商集合，包含 **Report ID 19**（0x13）的 19 字节输入/输出报告，以及 Report ID 6 的 7 字节 Feature 报告。

本程序只使用接口 1 的 Report ID 19 输出报告。识别条件：

1. VID/PID 与上表一致；
2. `HID_NAME` 精确匹配 `Compx 2.4G Wireless Receiver`；
3. 报告描述符同时包含厂商页 `06 02 FF` 与 `85 13`（Report ID 19）。

USB 有线时键盘同样枚举为 `05ac:024f`，但产品字符串是 `BY Tech MCHOSE K99 Gaming Keyboard`：

- 接口 0：启动键盘，无 Report ID，只有一个 64 字节 Feature 报告；不要使用；
- 接口 1：厂商集合，包含 Report ID 6 的 **519 字节 Feature 报告**（另外还有 Report ID 3/4/5 等输入/输出集合），有线配置读写全部走这个报告。

有线识别条件：

1. VID/PID 与上表一致；
2. `HID_NAME` 包含 `MCHOSE`；
3. 报告描述符中有 Usage Page `0xFF00`、Report ID `6`、Feature 主项，且 `Report Count × Report Size / 8 = 519`。

这样不会误接管真正的 Apple 键盘，也不依赖 `/dev/input` 事件。

## 2. 2.4G 报文格式

一次 HID 输出报告共 20 字节：

```
[0x13] [cmd] [total] [index] [YY] [14 字节数据] [checksum]
```

- `0x13`：HID Report ID。
- `cmd`：命令字节。
- `total`：该命令的总包数，从 1 开始。
- `index`：包序号，从 0 开始。
- `YY`：
  - 低半字节：本包有效数据长度（0..14）；
  - 高半字节：按键图层（仅键表读写使用；0=默认，1=Fn，2=Fn2）。
- `checksum` = (`0x13` + 前 18 字节之和) mod 256。
- 每个包的 14 字节数据区不足时补 0；`YY` 的低半字节告诉设备有效长度。

输入报告同样为 Report ID 19 + 19 字节载荷，载荷结构与上表一致；读取时按 `total` 收集 `index` 0..total-1，并取每包 `YY & 0x0F` 个字节拼接。

## 3. 2.4G 读命令

读命令的 19 字节载荷通常为：

```
[cmd] [0x01] [0x00] [selector] [0x00 ...]
```

其中 `selector` 仅键表命令使用。HID 报告需要在最前面加 Report ID。

| 数据 | cmd | selector | 返回包数 | 数据长度 |
|---|---:|---:|---:|---:|
| 性能设置 | `0x44` | 0 | 10 | 128 |
| 键表（默认层） | `0x41` | `0x00` | 36 | 504 |
| 键表（Fn 层） | `0x41` | `0x10` | 36 | 504 |
| 键表（Fn2 层） | `0x41` | `0x20` | 36 | 504 |
| 灯效 | `0x49` | 0 | 35 | 490 |
| 电量 | `0x4A` | 0 | 1 | 2 |
| 自定义逐键灯效 | `0x42` | 0 | 27 | 378 |
| 快捷指令表 | `0x43` | 0 | 37 | 512 |
| 密码（未使用） | `0x05` | 0 | 1 | 10 |

快捷指令是**唯一**在数据区带描述子的读命令，其它读命令数据区全为 0：

```
13 43 01 00 10 03 02 00 00 00 00 00 00 00 00 00 00 00 00
```

例：读取 Fn 层的完整输出报告（20 字节）：

```
13 41 01 00 10 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
        ^^ selector 在 Report ID 之后的第 5 个字节（载荷索引 3）
```

> 注意：selector 必须放在载荷索引 3。放到索引 4 会被设备忽略，三层都会返回默认层；这是一个实际踩过的坑。

读响应没有 ACK；设备直接发送数据包。长读（键表 36 包、灯效 35 包）可能丢包，客户端需要超时重发。本实现每次读取最多重试 3 次，并在每次重试前清空输入缓冲区。

## 4. 2.4G 写命令

写数据先序列化为 `[cmd] + 数据`，去掉 cmd 后按 14 字节分块。每包写入后设备会回一个同 `cmd`、同 `index` 的输入报告作为 ACK；客户端等待 ACK（超时重试）。

| 数据 | cmd | 数据长度 | 分包数 | 最后一包 YY |
|---|---:|---:|---:|---|
| 性能 | `0x04` | 128 | 10 | 实际剩余字节数 |
| 键表 | `0x01` | 512 | 37 | `(layer << 4) \| 有效字节数` |
| 灯效 | `0x09` | 518 | 37 | 去掉尾部 0 后的有效字节数 |
| 自定义逐键灯效 | `0x02` | 378 | 27 | 14（所有包固定 14） |
| 快捷指令表 | `0x03` | 变长（≤512） | 长度/14 向上取整 | 实际剩余字节数 |

键表 512 字节：

```
113 × 4 字节按键 + 58 字节 0x00 + 0x5A 0xA5
```

灯效 518 字节：

```
490 字节灯效数据 + 14 字节 0x00 + [00 00 5A A5 00 00 00 00 00 00 00 00 00 00]
```

非最后一包的 YY 为 14；键表非最后一包为 `(layer << 4) | 14`。最后一包的 YY 低半字节为实际有效字节数；若最后一包全 0，键表 YY 为 0。

写入后客户端会立即回读并逐字节比较；不一致则报错。真机幂等写回已验证。

## 6. 键表结构

504 字节返回数据 = 113 个 4 字节记录 + 52 字节尾部保留。前 113 个记录与型号键表的矩阵顺序一致；K99 V2 的 99 个物理键对应其中 99 个槽，其余 14 个是空格槽（space1..space14）。

每条 4 字节记录：

```
[type] [code1] [code2] [code]
```

从公开客户端和真机观察到的常见编码：

| 功能 | 4 字节 |
|---|---|
| 普通键 Esc | `00 00 00 29` |
| 左 Ctrl | `00 01 00 00` |
| 左 Shift | `00 02 00 00` |
| 鼠标左键 | `01 01 01 00` |
| 播放/暂停 | `02 00 00 CD` |
| 复制（Ctrl+C） | `00 01 06 00` |
| 宏（引用槽位） | `03 …` |
| Fn 层切换 | `0D 00 00 00` / `0D 01 00 00` |

不同动作的 `type/code` 语义不完全统一；本客户端使用公开客户端的动作表生成候选动作，并在界面上按取值匹配显示。未知值会保留原值，不会在改其它键时被覆盖。

三层共用同一组 113 个槽，通过读命令 selector 与写命令 YY 高半字节区分：

| 图层 | 读 selector | 写 YY 高半字节 |
|---|---:|---:|
| 默认 | `0x00` | 0 |
| Fn | `0x10` | 1 |
| Fn2 | `0x20` | 2 |

## 8. 电量

2 字节：

- byte 0：电量百分比（0..100）；
- byte 1：状态位。官方解析器声明为 `bit4("fullStatus").bit4("chargeStatus")`，其位序从高位起排，所以**高半字节 = fullStatus（已充满）、低半字节 = chargeStatus（充电中）**；官方前端用 `chargeStatus === 1 && 电量 < 100` 判“充电中”图标。
- 真机三个样本在该解释下自洽：无线 50% = `0x01`（在充、未满）、有线 100% = `0x10`（满电停充）、有线 100% = `0x11`（在充且满）。客户端显示充电状态，并在充电位翻转时弹提示。

## 9. 无线休眠与唤醒

无线模式下键盘空闲后会关闭厂商通道，但接收器仍在 USB 上。此时读命令超时，而设备仍然“存在”；按键盘任意键可唤醒，客户端提示唤醒后重试，且不会因为读超时而断开设备。

客户端用一次短探测（1 次尝试、700 ms）判定休眠，而不是让每条读命令各堵满 3 轮超时：进入休眠态后跳过整轮读取，插拔扫描放缓到 1.5 秒（醒着时 0.9 秒），因此**插入有线后约 1.5 秒内就会切到有线链路**（键盘要推到 OFF 档才走有线，所以有线一旦出现时 2.4G 通道必然不在响应）。窗口不在前台时暂停扫描，回到前台立刻补扫一次。任何一次请求前都会再探测一次，通了就恢复正常读取。

## 10. USB 有线协议

有线使用 HID Feature Report，不使用 2.4G 的 20 字节输出报告：

- Report ID：`6`
- Feature 报告长度：`519` 字节
- ioctl 缓冲区：`520` 字节 = Report ID + 519 字节载荷

Linux ioctl（缓冲区大小参与编码请求码，64 位系统）：

```c
#define HIDIOCSFEATURE_520 _IOWR('H', 0x06, 520)  // 0xc2084806
#define HIDIOCGFEATURE_520 _IOWR('H', 0x07, 520)  // 0xc2084807
```

请求载荷（519 字节）：

```
[cmd] [space0 6 字节] [数据] [0 填充]
```

响应载荷（519 字节，已去掉 Report ID）：

```
[cmd] [space0 6 字节] [数据] [填充]
```

数据从载荷偏移 7（即 ioctl 缓冲区偏移 8）开始。响应必须回显 `cmd`；`space0` 不保证与请求一致（电量响应固定为 `00 00 01 00 02 00`），客户端只校验命令字节。

读命令：

| 数据 | cmd | space0 | 数据长度 |
|---|---:|---|---:|
| 电量 | `0x87` | `00 00 01 00 02 00` | 2 |
| 性能设置 | `0x84` | `00 00 01 00 80 00` | 128 |
| 键表 | `0x83` | `layer 00 01 00 F8 01` | 504 |
| 灯效 | `0x8A` | `00 00 01 00 00 02` | 490 |
| 自定义逐键灯效 | `0x86` | `00 00 01 00 7A 01` | 378 |
| 快捷指令表 | `0x82` | `00 00 01 00 00 02` | 512 |

`space0` 的第 5-6 字节是声明的读取长度（小端）：378 = `7A 01`，512 = `00 02`。官方对 `0x82` 的模板只声明了 4 字节且从未被前端调用，因此本客户端按 `getLightColor` 的形状声明整块 512 字节；**这条声明尚未在真机验证**。

键表读回 504 字节，前 452 字节为 113 个按键记录，其余 52 字节忽略。图层放在 space0 首字节（0=默认，1=Fn，2=Fn2）。

写命令（请求总长固定 519 字节）：

| 数据 | cmd | space0 | 载荷 |
|---|---:|---|---|
| 性能 | `0x04` | `00 00 01 00 80 00` | 128 字节性能数据 + 384 字节 0 |
| 键表 | `0x03` | `layer 00 01 00 F8 01` | 512 字节键表（113×4 + 58×0 + `5A A5`） |
| 灯效 | `0x10` | `00 00 01 00 00 02` | 490 字节灯效 + 16×0 + `5A A5` + 4×0 |
| 自定义逐键灯效 | `0x06` | `00 00 01 00 80 01` | 378 字节逐键表（长度字段写 384 = 6 字节前缀 + 378） |
| 快捷指令表 | `0x05` | `00 00 1 0 lenL lenH` | 指令表原文，超过 512 字节拒绝写入 |

有线写入没有 ACK 包。客户端发送后等待约 200 ms 再回读校验；读取命令发送后等待约 60 ms 再取 Feature 报告。首次打开接口时偶发一次 `EPROTO`，客户端会对 Feature 写入做 3 次有限重试。

## 11. 自定义逐键灯效表（378 字节）

- 结构是**三张平面表**，不是每键 3 字节交错：红 126 + 绿 126 + 蓝 126。
- 下标是 **113 个矩阵槽**（与键表同一套下标，即 `data/models/k99_v2.json` 的 `matrix` 顺序），113…125 由固件保留。默认层 / Fn / Fn2 共用这张表，不分层。
- 没有亮度字节、没有表头、没有 `5A A5` 结尾；全 0 表示该键不亮。
- 无线：读 `0x42`（27 包 / 378 字节），写 `0x02`，所有包 YY 固定 14。有线：读 `0x86`（space0 长度 378），写 `0x06`（space0 长度 384 = 6 字节前缀 + 378）。
- 每次改动整表回写（官方也是逐键点击即整表下发），写入后回读逐字节比较。
- 界面上点击一个键：颜色等于当前调色板色时清除，否则设为该色。

## 12. 快捷指令表（512 字节）

「目录 + 正文」的变长结构，不是定长槽位数组：

```
目录：K 项 × 4 字节 = [addrL addrH][lenL lenH]      （小端）
正文：紧跟目录，按目录顺序排列，每条 = [nameLen u8][UTF-8 名称][节点 × n]
```

- `addr[0] = 4 × K`，其后 `addr[i] = addr[i-1] + len[i-1]`；解析时用 `addr[0] / 4` 得到条数。全 0 表示空表。
- 节点 4 字节：

| 字节 | 内容 |
|---|---|
| 0 | bit7 抬起(1)/按下(0)；bit4-2 类型（0=普通键、1=扩展键 usage≥100、2=鼠标）；bit2-0 延时高 3 位 |
| 1 | 延时中 8 位 |
| 2 | 延时低 8 位 |
| 3 | 键码：HID usage，或鼠标位掩码（左 1 / 右 2 / 中 4 / 后退 8 / 前进 16） |

- 延时 = `((b0 & 7) << 16) | (b1 << 8) | b2`，单位 ms，含义是**本节点之后**的间隔。表里没有独立的延时记录：界面上的延时节点在编码时回填到前一个按键记录，首个延时和 0 延时不落盘。
- 名称以 UTF-8 原文存入设备，界面限制 2–15 个字符。
- **执行类型不在表里**，在引用它的按键动作中：`[03] [类型] [01] [槽位]`，类型字节 4=按住时循环、2=循环至任意键按下、1=执行一次；槽位是该条指令在表中的下标。
- 所以分配一条指令要写两处：先写指令表，再写引用它的键表；本客户端在一次请求里按这个顺序完成。指令表写完不做回读校验（读不回来，无从校验），键表仍逐条回读比对。删除一条时更高的槽位号会前移，引用它们的按键同时被重写，剩余引用不会错位。
- 这张表**读不回来**：官方前端的 `getMacro` 只声明了 4 字节解析器且从未调用，真机有线读 `0x82` 返回的 512 字节装的是键表内容（`00 10 00 00 | 00 00 00 29 | 00 00 00 35 | 00 00 00 2b …`，正是 matrix 序的默认层记录）。因此指令名称与节点存在本机 `~/.config/mchose_hub_linux/commands.json`（Flatpak 下为 `~/.var/app/top.ddmt.mchosehub/config/`），键盘里只存表、按键上只留槽位号——与官方同一套语义。

## 13. 验证记录

2026-10-25，K99 V2 + Compx 2.4G 接收器：

- `--probe`：电量 50%，回报率 1000 Hz，休眠 3 分钟，灯效模式 11，三层键表读取成功；
- `--probe-write`：性能 128 字节、三层键表 512 字节、灯效 518 字节原样写回并回读一致；
- UI：Win 键锁开→关，设备页状态回读一致；模拟设备下测试了按键禁用、灯效模式切换与性能写入。

2026-10-25，K99 V2 USB 有线（`/dev/hidraw5`，519 字节 Feature Report）：

- `--probe`：电量 100%（状态 `0x10`），回报率 1000 Hz，休眠 3 分钟，灯效模式 11，默认层 102 个非空键、Fn 层 38 个非空键、Fn2 层为空；
- `--probe-write`：性能 519 字节、三层键表各 519 字节、灯效 519 字节原样写回；性能 128 字节、三层键表 452 字节和灯效 490 字节回读逐字节一致。

2026-10-27，快捷指令与自定义逐键灯效（**仅模拟设备与静态断言，真机未验证**）：

## 14. 参考实现边界

- 本协议覆盖 K99 V2 的键表、性能、灯效、电量、自定义逐键灯效与快捷指令。OTA 固件升级、密码握手 `0x05`、设备端恢复出厂 `0x06` 未实现。
- 官方把宏的名称与执行类型存在前端自己的 localStorage 里，删除条目也不下发设备，键盘上旧指令会继续触发。本客户端删除时重写指令表、把引用该槽位的按键置为禁用、并把更高槽位号前移；本机与键盘因此始终同步。
- **有线指令表读不可用（2026-10-28 实测）**：同一台键盘上逐键灯效 `0x86` 读取正常（Esc/A/W/S/D 与方向键默认蓝），而 `0x82` 返回的是键表内容，无法当作指令目录解析。程序因此不再依赖这条读：名称与节点存本机，写入不做回读校验；若键盘上存在本机不认识的被引用槽位（例如在官方 HUB 里做的），保存前会弹确认说明哪些槽位会被覆盖。
- `MCHOSE_HUB_TRANSPORT=wireless|wired` 可让 `--probe` 强制走一条链路，用于分别核对两种传输的读取差异。
- 快捷指令表按需读取（进入按键页或打开编辑器时），不在连接/刷新路径上。
- 未分配的快捷指令也会写进设备表（官方只在分配时写）。设备上多出来的未被引用条目不会触发，重新读取后会出现在指令列表里。
- 不同接收器/固件版本的命令字节可能不同；请以 `--probe` 输出为准，不建议盲目复用。
